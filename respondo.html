respondo JSON · v2.2.0

Consistent JSON API responses for Rails, in one line.

RubyGems GitHub Changelog MITRuby 2.7+

Install

# Gemfile
gem "respondo"
bundle install
rails generate respondo:install

The generator is an interactive wizard that writes config/initializers/respondo.rb. You do not need to include anything in ApplicationController; a Railtie loads the helpers for you.

Your first response

class UsersController < ApplicationController
  def index
    render_ok(data: User.all, message: "Users fetched")
  end

  def create
    user = User.new(user_params)
    if user.save
      render_created(data: user, message: "Account created")
    else
      render_unprocessable(message: "Validation failed", errors: user.errors)
    end
  end

  def show
    render_ok(data: User.find(params[:id]), message: "User found")
  rescue ActiveRecord::RecordNotFound
    render_not_found(message: "User not found")
  end
end

Response shape

Every response has the same four keys. Error responses add an errors hash.

KeyTypeDescription
successBooleantrue or false, always present
messageStringHuman-readable description
dataObject / Array / nullThe payload
metaObjectTimestamp, pagination, optional request_id
errorsObjectErrors only: { field: ["message"] }
{
  "success": true,
  "message": "Post published",
  "data": { "id": 42, "title": "Hello World" },
  "meta": { "timestamp": "2024-06-15T10:30:00Z" }
}
{
  "success": false,
  "message": "Validation failed",
  "data": null,
  "errors": { "email": ["is invalid"], "name": ["can't be blank"] },
  "meta": { "timestamp": "2024-06-15T10:30:00Z" }
}

Pagination

Pass a pagination: hash and it lands in meta.pagination for every endpoint.

def index
  @posts = Post.published.page(params[:page]).per(params[:per_page] || 20)

  render_ok(
    data:    @posts,
    message: "Posts fetched",
    pagination: {
      current_page: @posts.current_page,
      next_page:    @posts.next_page,
      prev_page:    @posts.prev_page,
      total_pages:  @posts.total_pages,
      total_count:  @posts.total_count,
      per_page:     @posts.limit_value
    }
  )
end

Serialization

Respondo converts what you pass to data: automatically.

InputOutput
ActiveRecord::Base instancerecord.as_json
ActiveRecord::RelationArray of as_json records
ActiveModel::Errors{ field: ["message", …] }
Hash / ArrayPassed through, values serialized recursively
Exception{ message: e.message }
Responds to #as_json / #to_hCalls it
String, Integer, …As-is
Don't expose raw models

record.as_json includes every column, such as password_digest, API tokens and internal flags. Return an allow-listed shape in production.

render_ok(data: user.as_json(only: %i[id name email]))

# or configure one serializer for the whole app
config.serializer = ->(obj) { UserBlueprint.render_as_hash(obj) }

Set config.strict_serialization = true to make Respondo raise Respondo::UnsafeSerializationError whenever a raw model or relation is passed without a serializer. Without it, a one-time warning is logged per model class.

Using your own serializer

Respondo does not replace your serializers. It only wraps the response in the standard shape (success, message, data, meta). Whatever you pass as data: ends up in data, so use whichever style fits your API.

def index
  render_ok(data: User.all, message: "Users fetched")
end

Models and relations are converted with as_json, which includes every column. That is fine for quick prototypes; for production prefer a serializer or an allow-list.

class UsersController < ApplicationController
  def show
    user = User.find(params[:id])
    render_ok(data: UserSerializer.new(user).as_json, message: "User fetched")
  end
end

class ProfilesController < ApplicationController
  def show
    profile = current_user.profile
    render_ok(data: ProfileSerializer.new(profile).as_json, message: "Profile fetched")
  end
end

class BookingsController < ApplicationController
  def index
    bookings = current_user.bookings.page(params[:page]).per(20)
    data = bookings.map { |b| BookingSerializer.new(b).as_json }
    render_ok(data: data, message: "Bookings fetched")
  end
end

Use the serializer you already have for each resource: a UserSerializer, a ProfileSerializer, a BookingSerializer, or Blueprinter / ActiveModelSerializers output. Respondo takes the hash or array you give it and wraps it, so you control exactly which fields are exposed.

Prefer to set one serializer for the whole app instead? Use config.serializer (see Configuration). It is optional.

Configuration

Run rails generate respondo:install or write the initializer by hand:

# config/initializers/respondo.rb
Respondo.configure do |config|
  config.default_success_message = "OK"
  config.default_error_message   = "Something went wrong"
  config.include_request_id      = true   # adds request_id to every meta
  config.camelize_keys           = true   # snake_case → camelCase
  config.default_meta            = { api_version: "v1" }
  config.strict_serialization    = true   # raise on raw ActiveRecord data (recommended)
  config.max_collection_size     = 1_000  # raise instead of loading huge collections
end
OptionDefaultPurpose
default_success_message"Success"Message when none is passed to a success helper
default_error_message"An error occurred"Message when none is passed to an error helper
include_request_idfalseAdds request_id to meta
camelize_keysfalsesnake_case to camelCase in data and meta
default_meta{}Merged into every meta
serializernilA callable used to serialize data
strict_serializationfalseRaise on raw ActiveRecord objects
max_collection_sizenil (no limit)Raises CollectionTooLargeError; relations are capped with LIMIT max+1

request_id and timestamp are always generated by Respondo; values passed through meta: or default_meta cannot override them.

camelCase output

Ideal for Flutter and React Native clients. If two keys collapse to the same camelCase name (user_id and userId), both are left untouched rather than one overwriting the other.

{
  "success": true,
  "data": { "firstName": "Alice", "createdAt": "2024-01-01" },
  "meta": { "totalPages": 4, "currentPage": 1 }
}

HTTP helpers

There is a helper for every HTTP status code. These are the ones you will reach for most.

2xx success

render_created201A POST created a resource

Global error handling

Handle exceptions app-wide from ApplicationController, with no try/rescue in every action.

class ApplicationController < ActionController::API
  rescue_from ActiveRecord::RecordNotFound do |e|
    Rails.logger.info(e.message)
    render_not_found(message: "Resource not found")
  end

  rescue_from ActionController::ParameterMissing do |e|
    Rails.logger.info(e.message)
    render_bad_request(message: "Required parameter missing")
  end

  rescue_from StandardError do |e|
    Rails.logger.error(e.full_message)
    render_server_error(message: "An unexpected error occurred")
  end
end
Use fixed messages

e.message contains model names and lookup keys (Couldn't find User with 'id'=42), which helps attackers enumerate your schema. Log it, don't return it.

Security defaults

Since 2.2.0, Respondo is hardened against the issues found in an independent security assessment:

  • Install generator validates default_meta keys and backs up an existing initializer to respondo.rb.bak instead of overwriting it.
  • Raw model exposure is flagged or blocked via strict_serialization.
  • meta can't spoof request_id or timestamp.
  • Redirect helpers only accept relative or same-host targets.
  • Unbounded collections can be capped with max_collection_size.

Full details are in the changelog.
